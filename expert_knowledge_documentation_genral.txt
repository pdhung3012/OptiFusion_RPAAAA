Expert Knowledge Documentation: PolyBench 2mm
Static optimization analysis of PPCG, PLUTO, Gemini, and GPT-5.2 outputs
Scope. This document analyzes the supplied 2mm implementations qualitatively for likely speedup behavior. It compares the generated loop structure, OpenMP strategy, tiling, vectorization, locality, and overhead. It does not report measured runtime speedups; performance conclusions should be validated on the target hardware.
1. Application Characteristics
2mm computes two consecutive dense matrix multiplications: tmp = α·A·B, followed by D = β·D + tmp·C. The kernel is compute intensive and has substantial reuse potential, so performance is strongly affected by cache locality, parallel work distribution, vectorization, and the overhead of entering OpenMP regions.
Most useful parallelism: independent output rows/cells of tmp and D.
Most useful locality optimization: block/tile the matrix-multiplication loops so A/tmp blocks and portions of B/C remain cache-resident.
Most useful low-level optimization: SIMD/vectorization of contiguous inner loops when legal and profitable.
Key risk: a transformation can increase loop-control complexity or scheduling overhead enough to offset locality gains, especially for small problem sizes.

3. Approach-by-Approach Expert Analysis
3.1 PPCG
Observed optimization. The OpenMP version parallelizes the outer i dimension separately for the two matrix-multiplication phases. The tiled version keeps OpenMP parallelism but introduces 32×32-style blocking across the output and reduction dimensions, with boundary handling through min/max expressions.
Advantages for speedup
Both phases expose coarse-grained row/block parallelism with no reduction synchronization between threads because each thread updates disjoint output elements.
The tiled version can substantially improve temporal and spatial cache locality by reusing blocks of A, B, tmp, and C before moving to the next tile.
Blocking the reduction dimension can reduce cache misses and memory-bandwidth pressure, which is especially valuable for dense matrix multiplication.
The transformation is systematic and dependence-aware, making it suitable as a reliable baseline for legal loop restructuring.
Disadvantages / risks
The untiled OpenMP version leaves the original memory-access pattern mostly intact, so B and C accesses can still suffer poor cache locality as matrices grow.
The tiled version fixes the tile size at 32; this may be suboptimal for a particular cache hierarchy, data type, thread count, or matrix size.
Boundary min/max logic and deeper loop nesting add control overhead. For small matrices, this overhead can offset tiling benefits.
Two separate OpenMP parallel-for regions introduce fork/join overhead between the tmp and D phases.
Expert knowledge. For 2mm, PPCG’s tiled output is generally the more promising performance template than its simple OpenMP output when matrices are large enough to benefit from cache blocking. The most reusable idea is to combine coarse thread-level parallelism with cache-sized blocking, while tuning the tile size rather than assuming 32 is universally optimal.
3.2 PLUTO
Observed optimization. The non-tiled output applies polyhedral rescheduling, OpenMP parallel loops, and explicit vectorization directives. It also restructures initialization and computation. The tiled output adds 32-sized tiles and fuses/reorders several operations into a more complex generated schedule.
Advantages for speedup
PLUTO can exploit more transformation freedom than simple pragma insertion, including loop fusion, reordering, parallelization, and vector-friendly loop formation.
Explicit ivdep/vector directives can help the compiler generate SIMD code for contiguous inner loops, increasing arithmetic throughput.
The tiled version improves locality across the two dense multiplication stages and exposes cache-blocked computation similar to optimized GEMM structure.
Fusing initialization/scaling with surrounding transformed loops may reduce extra full-array passes and improve cache reuse in favorable cases.
Disadvantages / risks
The generated control structure is much more complex, with many bounds, conditionals, and transformed induction variables; this increases instruction overhead and makes performance sensitive to problem dimensions.
Aggressive fusion/reordering can create less intuitive access patterns and may not always map cleanly to the target cache/microarchitecture despite being dependence-correct.
The tiled output again uses a fixed tile size of 32, which may not match the best hardware-specific block size.
Generated code size and branch complexity can reduce instruction-cache efficiency and make compiler auto-optimization/debugging more difficult.
Expert knowledge. PLUTO is valuable when 2mm benefits from aggressive affine transformations beyond basic OpenMP. Its strongest reusable ideas are vector-friendly inner loops and legal fusion/reordering, but these should be retained only when profiling confirms that the extra schedule complexity beats a simpler tiled implementation.
3.3 Gemini
Observed optimization. Gemini preserves the original two-phase loop structure and adds one OpenMP parallel-for to each outer i loop, with j and k private. No loop collapse, tiling, explicit scheduling policy, or SIMD directive is added.
Advantages for speedup
The transformation is simple and low risk: each i row is independent, so outer-loop parallelization maps naturally to the kernel.
Low transformation complexity keeps loop-control overhead small and preserves compiler-friendly, readable code.
Using a parallel outer row loop gives each thread substantial work for medium/large matrices, which can amortize OpenMP scheduling cost.
The original numerical operation order inside each output element is preserved, reducing the chance of unexpected numerical differences from aggressive reordering.
Disadvantages / risks
Parallelizing only i may expose insufficient parallelism when NI is small relative to the thread count.
Two independent parallel-for directives create two separate parallel regions and therefore additional fork/join overhead.
No cache tiling is introduced, so the implementation misses a major optimization opportunity for the B/C access streams in large matrices.
No explicit SIMD/vectorization guidance is provided, leaving vectorization entirely to the downstream compiler.
Expert knowledge. Gemini provides a strong simplicity-first baseline. Its output is appropriate when thread-level parallelism alone is sufficient, but for high-performance 2mm the main missing knowledge is cache blocking and broader work sharing. A useful refinement would preserve the simple structure while adding tiling and/or collapse only when needed.
3.4 GPT-5.2
Observed optimization. GPT-5.2 creates a single OpenMP parallel region and uses two work-sharing loops with collapse(2) and schedule(static), parallelizing the i–j output space for both multiplication stages while keeping k private.
Advantages for speedup
A single parallel region can reduce repeated OpenMP team creation/destruction relative to two independent parallel-for regions.
collapse(2) exposes NI×NJ (and NI×NL) tasks instead of only NI tasks, improving thread utilization when the number of rows is not large enough by itself.
schedule(static) is a good fit for regular dense matrix multiplication because iterations have nearly uniform work, minimizing scheduler overhead.
The code remains much simpler than polyhedral tiled output, giving a favorable balance between parallelism and maintainability.
Disadvantages / risks
collapse(2) increases work-sharing granularity but does not fix memory locality in the reduction dimension; cache behavior of B and C remains a bottleneck.
For very large NI, outer-i parallelism may already provide enough work, so collapse(2) may add bookkeeping without meaningful scalability benefit.
No cache tiling or explicit vectorization is introduced, leaving significant matrix-multiplication optimization potential unused.
The implicit barrier between the two omp-for loops is required by the tmp dependency; although correct, it means the two stages cannot freely overlap.
Expert knowledge. GPT-5.2 demonstrates a useful OpenMP optimization rule for 2mm: reuse one parallel region and statically distribute the full output space when outer-loop parallelism is insufficient. For maximum speed, this strategy should be combined with cache blocking and compiler/SIMD-friendly inner loops rather than used alone.

5. Recommended Knowledge Rules for Optimizing 2mm
Prioritize cache blocking because 2mm is dominated by two dense matrix multiplications; thread parallelism alone does not address the main locality bottleneck.
Parallelize independent output rows/tiles. Use collapse(2) when NI alone does not provide enough parallel work, but avoid unnecessary collapse when row-level parallelism already saturates the machine.
Prefer one persistent OpenMP parallel region across the two dependent phases when practical, with a barrier between phases, to reduce repeated fork/join overhead.
Use static scheduling for the regular, balanced iteration space unless measurements show load imbalance.
Choose tile sizes according to cache capacity, data type, matrix dimensions, and thread count; treat 32 as a candidate rather than a universal constant.
Keep the innermost loops simple and vectorizable. Favor contiguous accesses and explicit SIMD/vector guidance when the compiler needs help.
Profile aggressive polyhedral fusion/reordering against a simpler tiled OpenMP baseline; legal transformations are not automatically faster on every architecture.
Validate numerical equivalence after transformations, especially if future optimizations alter floating-point reduction order.

2. Application Optimization Characteristics
Three dense matrix multiplications are executed in sequence: E=A×B, F=C×D, and G=E×F. E and F are independent of one another, while G depends on both. The kernels have high arithmetic intensity and regular memory access, making loop blocking, SIMD/vectorization, and coarse-grained thread parallelism particularly relevant.

4. Cross-Approach Synthesis
The compiler-generated variants emphasize dependence-aware affine transformations and, in their tiled versions, explicit locality optimization. The LLM-generated variants generally favor simpler OpenMP edits that preserve the original program structure. This simplicity can reduce transformation overhead and improve maintainability, while PPCG/PLUTO can expose locality and legal parallelism that are difficult to derive from a local pragma insertion alone.
A strong SmartCompiler-style strategy should therefore combine the two: retain compiler legality/dependence knowledge for tiling and scheduling, but prefer the simplest parallel structure that achieves the required locality and thread utilization on the target machine.
5. Reusable Expert Knowledge for Speedup
Prioritize cache blocking for all three matrix products; a tile size around 32 is a reasonable starting point but should be tuned to cache size and data type.
Use one persistent OpenMP parallel region when possible to avoid repeatedly creating thread teams across E, F, and G.
Preserve the dependency barrier before G, but E and F may be computed concurrently using OpenMP sections/tasks when resources and matrix sizes justify it.
Keep the reduction/accumulation dimension innermost or otherwise structured to maximize vectorization and reuse.
Combine thread-level parallelism with SIMD rather than relying on OpenMP outer-loop parallelism alone.
For small problem sizes, avoid excessive collapse, tasking, or many parallel regions because runtime overhead can dominate.
